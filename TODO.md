## Правила ведения

- После выполненной задачи — `[x]` и номер PR / хеш коммита.
- Задача стала неактуальной — зачеркнуть `~~...~~` с пометкой **почему**, не удалять.
- Поля пункта — инлайн-теги `@owner:` / `@blocked_by:<repo>#<slug>` / `@trigger:"…"`,
  все опциональны: пустое поле означает «неизвестно» и это честнее выдуманного значения.
- `@id:<node-id>` — канонический идентификатор пункта (ADR-ECO-005 PF-2B): строчная
  грамматика `[a-z0-9][a-z0-9._-]{0,63}`, из него строится URI
  `todo://github-checker/<id>`.
- **Теги и суть пункта — на одной строке с `- [ ]`**: парсер разбирает пункт построчно и
  продолжений ниже не видит. Отступленные строки под пунктом — контекст для человека.

- [x] Merge-gate: три новых глагола `pr-detail`/`merge`/`post-merge-sync` @id:merge-gate-verbs
      Fail-closed squash-merge за девятью предикатами (`open`, `not-draft`,
      `mergeable`, `checks-green`, `checks-complete`, `approvals`,
      `threads-resolved`, `threads-complete`, `squash-allowed`) плюс

      локального клона (никогда stash/reset/force). Документировано в
      `README.md`. (PR #14)
- [x] Inbox-issue verbs: `issue-lookup`/`issue-create` (ADR-ECO-006) @id:inbox-issue-verbs
      `issue-lookup` читает inbox-issue этого репо через `gh issue list
      --state all` (не `gh search issues`: индекс поиска пагинируется без
      исчерпывающего режима и может отставать от только что созданного
      issue, что важно — `issue-create` перечитывает сразу после создания;
      `gh issue list` бьёт прямо в API, нативно `--repo`-скоуплен и
      принимает настоящий `--state all`, в отличие от `gh search issues
      --state`, который отклоняет `all`); каждый кандидат подтверждается
      точным парсом структурного блока, а не доверием к лейблу. `--limit`
      щедрый, но реальный: попадание точно в кап трактуется как возможное
      усечение и фейлится закрыто, а не отдаёт частичный `matches` (тот же
      идиом, что `checks_truncated`/`threads_truncated` у `pr-detail`).
      `issue-create` сам строит канонический body из провалидированных
      `slug`/`from` — форма не может их подделать — и заново перепроверяет
      отсутствие дубля прямо перед созданием; если пречек находит НЕСКОЛЬКО
      claimant'ов, они не схлопываются в `[0]`, а всплывают в `matches` с
      `ok=false` для решения вызывающей стороны. `created` трёхзначен
      (`true`/`false`/`null`-unknown при обрыве транспорта); read-back после
      успешного create различает "не прочитался"/"прочитался, но пусто"/
      "прочитался, но malformed"/"прочитался, но несколько" как разные
      `detail`, а не одно сообщение. Документировано в `README.md`.
      (PR #15; ревью нашло Critical
      truncation-дыру + четыре fail-open дефекта, все закрыты в том же PR)

## Известные дефекты

- [x] Сьют падал на чистом раннере: bare-origin в тестах наследовал `init.defaultBranch` @id:test-localgit-ci-env-fragility @epic:eco.tooling
      Принятый inbox-запрос — issue #35 (от `devtools`, волна CI 2026-09-01,
      github-checker#34 job `test`). `tests/test_localgit.py` создавал bare-origin
      как `git init --bare` без `-b`, поэтому его HEAD брался из
      `init.defaultBranch` хоста. На машине владельца это `main` (Apple-овский
      system gitconfig), на ubuntu-раннере — `master`: клон такого origin
      приземлялся на неродившийся `master`, и `git push -q origin main` в
      `test_pull_ff_only_divergence_raises` падал с `src refspec main does not
      match any`. Не баг продукта — хрупкость фикстуры к окружению, и именно
      поэтому она была невидима локально. Починено закреплением ветки в
      хелпере `_init_bare_origin` (`git init --bare -b main`), три места;
      идентичности и `receive.denyCurrentBranch` оказались ни при чём (origin
      bare, identity тесты проставляют сами). Регрессия воспроизводится и
      проверяется прогоном сьюта с `GIT_CONFIG_SYSTEM`, где
      `init.defaultBranch = master`. (PR #36)

- [x] `argparse` ломает JSON-контракт на значениях флагов, начинающихся с `-` @id:argparse-dash-values
      Системный, сквозной по всему headless CLI дефект, не специфичный для
      `issue-lookup`/`issue-create`: `argparse` отвергает *любое* значение
      флага, начинающееся с `-` (например, `--slug --from`), как будто это
      отдельный неизвестный флаг — своим собственным `exit(2)` и
      usage-сообщением в stderr, вообще не печатая JSON. Это в обход
      валидации каждого хендлера и ломает контракт «ровно один JSON
      `ActionResult` на stdout», на который полагаются машинные
      потребители. Предсуществующий: воспроизводится и на давно живущем
      `merge --if-head`, этой веткой не внесён. Обходной
      путь на стороне вызывающего — `--flag=значение` вместо
      `--flag значение`. Настоящее исправление требует правки парсинга
      аргументов сразу по всему CLI, а не точечно под новые глаголы.
      **ЗАКРЫТО 2026-07-31 (PR #16)**: оказалось не пять
      отдельных дыр, а одна воронка — `ArgumentParser.error()`, через которую
      идут все отказы (значение с дефисом, неизвестный глагол, лишний и
      недостающий позиционный, неизвестный верхнеуровневый флаг). Подкласс
      `_JsonParser` поднимает `_ArgvRefused` вместо `exit(2)`, `main()` печатает
      обычный отказной `ActionResult` с извлечёнными `action`/`dir`. `--help`
      идёт через `exit()`, не через `error()`, поэтому остался вне контракта:
      exit 0, usage, без JSON. Предпосылка для заморозки `contracts/actions/v1`:
      замораживать envelope поверх пути, который его нарушает, значит издать
      заведомо ложный контракт.

- [ ] `ISSUE_LIST_LIMIT = 200` — медленный фитиль, не сегодняшний баг @owner:repo:github-checker @trigger:"the inbox issue count in a repository approaches 200" @id:issue-list-limit-fuse @epic:eco.tooling
      Список читается с `--state all`, а значит монотонно растёт: закрытые
      inbox-issue из него никогда не выпадают. Когда число `inbox`-issue в
      репо перевалит за 200, guard truncation (см. `issue-lookup` выше)
      начнёт фейлиться закрыто **постоянно** — и `issue-lookup`, и
      `issue-create` (он вызывает `issue-lookup` дважды) перестанут
      работать для этого репо, пока лимит не поднимут. Это не баг: гейт
      фейлится закрыто ровно так, как должен — отказ лучше, чем тихий
      частичный `matches`. Чинить нужно поднятием кап(а), а не ослаблением
      guard'а. Исчерпывающий маршрут при необходимости — `gh api
      --paginate` вместо `gh issue list --limit`, который постранично
      пройдёт весь список без верхней границы.
